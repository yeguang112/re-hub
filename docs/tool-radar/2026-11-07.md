## 3. 深度评估

### 3.1 `MG1937/rust_ASC` — Android 的“快查层”

**是什么** `[观察]` Rust 写的无状态 APK/DEX 反编译器与查询器，133★，Apache-2.0，v0.1.2-post1（2026-10-28），Black Hat Europe Arsenal 议题项目。`[推断]` 它直接 mmap APK、按需解压 DEX、并行跨 DEX 扫描，不建全局索引/磁盘缓存；提供 `listclass / listmethod / liststring / findrefs / getclass / getmanifest / export`，并用 `rust_ASC mcp` 暴露为 stdio MCP（每次调用起新进程）。

**对象 / 场景**
- objectType：`app` / subtype `android`
- 场景：**02-android-static**（静态）
- 最适合：拿到 APK 后的 30 秒侦察——类清单、字符串、谁引用了某个 URL/方法/字段、单类反编译、Manifest。

**优势**
- 速度与内存是按“查询”而不是“全量反编译”设计的：自述单类 70–118ms、字符串 xref 55–136ms；JADX 同任务 6s–8min；峰值内存 32–443MB vs JADX 1–13GB（TencentQQ 318MB 样本）。`[推断，未复现]`
- 无状态 → 适合 agent 批量跑几百个 APK，不会像 JADX 那样每次吃满内存。
- MCP 内置，接入 re-hub 的成本低（可走 `rehub_mcp`，也可写原生 adapter）。
- Apache-2.0，无商业许可障碍。

**劣势 / 边界**
- 输出是 **pseudocode**，不是 JADX 那种可读 Java；复杂方法/混淆还原不如 JADX。
- 只覆盖“代码查询/单类”，不做资源解码、重打包、动态、UI；不能替代 apktool/Frida。
- 年轻（0.1.2），只有 1 个 open issue，长期维护未知；MCP 每次 spawn 进程，批量会话有固定开销。
- 基准是作者自述，样本/脚本未在本机复现。

**vs 现有（JADX 1.5.6 / REA android provider）**

| 维度 | JADX | rust_ASC |
|---|---|---|
| 定位 | 全量反编译 + GUI | 无状态查询 + 单类 |
| 首次打开大 APK | 分钟级、GB 级内存 | 毫秒级查询、百 MB 级 |
| 输出可读性 | Java，较完整 | pseudocode，够定位 |
| 资源/重打包 | 资源有，重打包靠 apktool | 无 |
| Agent 接口 | 第三方 MCP/插件 | 内置 MCP |
| 成熟度 | 1.5.6，生态成熟 | 0.1.2，新 |

**结论：PILOT。** 不替换 JADX，新增一条“快查”能力：`android-apk` 计划第 1 步先 `asc` 做类/字符串/xref 侦察，命中目标类后再用 JADX 深反编译。这是低风险、可回退的增量。

### 3.2 `suffixing/apkscope` — Android 一体化（待验证）

**是什么** `[观察]` 单文件 `apkscope.exe`（10.7MB），Rust 从零写的 DEX 解析/反编译/资源/签名/MCP/GUI 一体工具，12★，Apache-2.0，v0.6.0（2026-11-05）。`[推断]` 命令覆盖 `scan / info / search / refs / decompile / callers / access / decrypt / dump / il2cpp / frida / rename / export / build`；16 个 MCP 工具；自带 viewer。

**对象 / 场景**
- objectType：`app` / `android`
- 场景：**02**（静态）、**03**（Frida/dump 动态）、**10**（重打包/签名）
- 最适合：不想装 JDK/JADX/apktool 的“一台机器一个 exe”场景；给 agent 做 Android 侦察 + 快速定位 + dump + 重签。

**优势**
- 能力面最宽：反编译、URL/secrets 扫描、xref、调用图、字段读写、字符串解密、Frida hook 生成、内存 dump、il2cpp 字符串定位、改包重签。
- 输出是 typed Java（作者对比 rust_ASC 的 pseudocode），可读性更好。
- 自带 MCP + viewer；Apache-2.0；作者写了“honest limits”，对复杂度有自知。
- 自述比 JADX 打开 TikTok 快 11×、内存少 9×；单类比 rust_ASC 快至 1.8×。`[推断，未复现]`

**劣势 / 边界**
- **12★、单人项目、0.6.0**，功能面却极大 → 长尾 bug 与维护风险高。
- 基准全部来自作者 `bench/`，没有第三方复现；这类“全面碾压”声明必须先打问号。
- 复杂方法回退 `goto`/Smali；viewer 只在 Windows 测过；`dump` 需 root + frida-server；`decrypt` 只处理常量可算的解密器；扫描是启发式，findings 不是 verdict。
- 与 JADX/apktool/Frida 全重叠，若引入必须明确“谁是 reference”。

**结论：PILOT（验证优先）。** 先拿一个已授权 APK 复现它的 3 个关键声明（打开速度、单类 Java 质量、MCP 调用），再决定是否作为“侦察/ dump”后端；JADX 继续做深度反编译的 reference。

### 3.3 `VAHPEM/rust-deobf` — Rust 恶意样本的去混淆补位

**是什么** `[观察]` Python 工具（PyPI `rust-deobf`），19★，core Apache-2.0，premium 模块 AGPL-3.0/商业双许可；无 GitHub Release，创建 2026-10-18。`[推断]` 静态 call-site 恢复 + Unicorn 模拟执行（只跑函数，不跑整样本），恢复 obfstr/litcrypt/cryptify/muddy/栈字符串/手写 XOR；带 `soc_triage.py`、FLOSS 兼容 JSON、Ghidra/IDA 注释桥、MCP server、YARA/capa 导出、UPX 静态脱壳。

**对象 / 场景**
- objectType：`software` / `windows-native`（也覆盖 ELF/Mach-O、x86-64/ARM64/x86）
- 场景：**01-native-binary**（静态）、**12-vuln**（恶意样本/补丁对比辅助）
- 最适合：Rust 编写的 stealer/loader/agent，字符串被 `obfstr`/`litcrypt`/`cryptify` 加密，`strings`/FLOSS 全空。

**优势**
- 打的是真空档：Rust 恶意样本增长，但 FLOSS 对主流 Rust 混淆 crate 基本无效；它自述 5/5 vs 0/5。
- 静态 + 模拟，不运行样本；对恶意分析是正确姿势。
- 不只是一把 strings：triage 卡片、crate 能力指纹、Ghidra/IDA 注释、检测规则导出，能嵌进现有链路。
- MCP + JSON，agent 可直接调用；core Apache-2.0。

**劣势 / 边界**
- 19★、无 release、作者自述大量“最强”结论（VMProtect/Themida devirtualizer、“exact source”），**可信度必须靠复现建立**。
- premium（VM 反虚拟化/CFF/MBA）是 AGPL/商业，不是纯 Apache；如果要用于商业交付要注意。
- Python 3.10+，依赖 Unicorn 等；对大样本的模拟可能超时/漏分支。
- 误报：解码出的字符串需要人工/证据确认，不能直接当 C2。

**结论：PILOT。** 用 1–2 个公开的 Rust 恶意样本（或自建 obfstr 样例）对拍 FLOSS + Ghidra，验证“恢复率/耗时/误报”，再决定是否作为第 01 章“Rust 二进制”子链路。

### 3.4 `Wtrwx/vesper` — iOS 的 MCP 补位

**是什么** `[观察]` Python 3.11+ 的 iOS 逆向平台，MIT，72★，无 release（源码安装）；host 需 macOS/Linux，目标需**越狱 iPhone** + SSH + Frida 17.5；可选 IDA 9+/Hex-Rays、Theos。`[推断]` 20+ MCP 工具：设备/SSH、UIKit 树与截图、Objective-C 类/方法/头文件、Swift 运行时、Frida attach/trace、`frida-ios-dump` 解密、classdumpc、IDA 反编译、Logos/Theos 插件开发与部署。

**对象 / 场景**
- objectType：`app` / `ios`
- 场景：**10-artifact**（IPA/Mach-O）、**14-dynamic**（Frida/LLDB，受限）、**15-ui**（UIKit 树/截图）
- 最适合：有越狱测试机的 iOS 深分析；re-hub 现在 iOS 只有“IPA 解包 + Mach-O 静态 + 受限动态”，Vesper 正好补动态与 UI。

**优势**
- 把 iOS 的 SSH/Frida/IDA/Theos 串成 MCP + Skill，和 re-hub 的“agent 调用工具”模型一致。
- MIT；有明确的安全边界（允许的 bundle ID、SSH host key、rootless 优先）。
- 覆盖“解密 → classdump → 动态 trace → 写 tweak”完整链路，不只是静态。

**劣势 / 边界**
- 硬门槛：越狱设备 + macOS/Linux host；Windows 用户直接用不了。
- 无 release，源码安装；Swift 支持实验性；IDA 需商业许可。
- 与 re-hub 的 iOS 章节是“补充”而非“替代”；没有设备时只能做文档/计划。

**结论：WATCH（有设备则 PILOT）。** 若你有越狱测试机，优先接；否则先把它写进第 10/14 章的“iOS 可选后端”，不阻塞主线。

### 3.5 `x86rc/unthemidator` — Themida 静态脱壳（许可缺失）

**是什么** `[观察]` 411★、v0.1.4（2026-10-28）、**无 LICENSE**；Windows/Unix CLI + 拖拽。`[推断]` 不运行样本、不调用目标 API/syscall；对 Themida / Code Virtualizer / WinLicense（v3–v4）做 PE 重建、资源解包、VM 解压、导入解密/IAT 恢复、版本识别、入口点定位；支持 x86/x64 的 exe/dll/sys。

**对象 / 场景**
- objectType：`software` / `windows-native`
- 场景：**14-dynamic**（脱壳，但它是静态方式）
- 最适合：被 Themida/WinLicense 保护、x64dbg 里 IAT 被抹、需要先还原成可调试 PE 的样本。

**优势**
- 正好补 re-hub 第 14 章“VMProtect/脱壳”只有方法没有专用后端的空白。
- 静态、不执行样本，适合恶意样本前置处理；输出“可运行/可调试”的 PE，后续可接 Ghidra/x64dbg。
- 411★ 说明需求真实存在；CLI 易接。

**劣势 / 边界**
- **无许可证 = 默认保留全部权利**，不能 vendor、不能改、不能随 re-hub 分发；只能“检测到用户自备则调用”。
- 只覆盖 Themida/CV/WinLicense，不是通用脱壳；VMProtect 不在此列。
- 发布两周、411★，热度与可信度需观察；无许可证，无法审计/复用。
- 脱壳的合法性/授权边界必须写清楚。

**结论：WATCH。** 在 `detect` 里加“可选外部工具”探测，文档写清“需用户自备、仅授权样本”；不进入 vendor，不默认安装。

### 3.6 `Zfinix/eleven` — Agent-first 桌面工作台（参考）

**是什么** `[观察]` 971★，Apache-2.0，v0.1.13（2026-10-22），TypeScript/GPUIX 桌面 app；macOS 14+ Apple Silicon、Windows x64、Linux x64。`[推断]` 任意 ACP agent（Claude/Codex/Gemini/Cursor/Copilot/OpenCode…）在同一窗口读代码、跟引用、改名、写注释、提议 patch；原生用 Ghidra（经 REA）或 Rizin，Android 用 jadx/apktool；带 LLDB 调试、函数级 diff、字节 patch、项目文件 `.eleven`。

**对象 / 场景**
- objectType：`software`（PE/ELF/Mach-O、GPU kernel、shader、模型）+ `app/android`
- 场景：**01**、**02**、**14**（LLDB）
- 最适合：人类分析师 + agent 同屏协作；需要“看代码、改名、打补丁、对比版本”的交互式工作。

**优势**
- 交互设计是本期最成熟的：agent 的每个改动有作者/可撤销，patch 以建议卡出现，人始终在环。
- 后端选择务实：Rizin 秒开做 triage，Ghidra 深反编译；Android 直接 jadx。
- 用 REA 作为执行层，和 re-hub 同源，说明“REA 作为后端”的路线被验证。
- Apache-2.0，可参考其 MCP 工具面与权限模型。

**劣势 / 边界**

### 3.8 `Huai-Tian/Exuvia` — Android 脱壳 + 修复

**是什么** `[观察]` 52★，AGPL-3.0，Rust，无 release，创建 2026-10-14。`[推断]` 两条产品线：① 静态解剖 + 把“真智能缺口”打包给外部 LLM 的工作单；② 动态采集（root、内核驱动物理内存 I/O、无 ptrace/injection、E2EE TCP、无 adb）；`repair` 把 dump 的 DEX 修回可启动 APK（清类、去织、方法体恢复、Manifest 手术、zipalign、v2 签名）。

**对象 / 场景**
- objectType：`app` / `android`
- 场景：**02**（静态壳识别）、**03**（动态 dump）
- 最适合：企业级壳/加固样本，dump 出来一堆 DEX 但装不回、起不来的情况。

**优势**
- 打的是“dump 之后”的空白：大多数工具只管 dump，不管修复成可运行 APK。
- 工具侧零 token、确定性判定；LLM 只处理真正的缺口，符合“证据/结论分离”。
- 壳家族无关，动态采集不依赖 adb/ptrace，隐蔽性设计明确。

**劣势 / 边界**
- **AGPL-3.0** + root + 内核驱动（KPM）+ 设备，集成/分发/合规成本高。
- 无 release、52★、文档密度大；实际壳覆盖未验证。
- 动态采集涉及内核，风险与授权边界必须严格。

**结论：WATCH。** 作为第 03 章“脱壳后修复”的参考；不在默认链路，不 vendor。若你有授权测试设备，可做一次隔离实验。

## 5. 横向对比：Android 四条链路

| 维度 | JADX 1.5.6 | rust_ASC 0.1.2 | apkscope 0.6.0 | dexsql 0.1.1 |
|---|---|---|---|---|
| 定位 | 全量反编译 reference | 无状态快查 | 一体化（含 GUI/Frida/重签） | SQL 查询 |
| 输出 | Java + 资源 | pseudocode | typed Java | 结构化结果 |
| 首次大 APK | 慢/吃内存 | 毫秒查询 | 快（自述 11× JADX） | 打开一次 ~0.38s |
| 全量反编译 | ✅ | 导出（radguard） | ✅ | ❌ |
| MCP | 第三方 | ✅ 内置 | ✅ 内置 | ✅ 内置 |
| 动态/dump | ❌ | ❌ | ✅（root） | ❌ |
| 重打包/签名 | 需 apktool | ❌ | ✅ | ❌ |
| 许可 | Apache-2.0 | Apache-2.0 | Apache-2.0 | NOASSERTION |
| 成熟度 | 高 | 低 | 低 | 低 |
| 建议 | 保留为深度 reference | **试点快查** | **试点侦察/dump** | 观察（许可） |

**结论：** 不建议“换掉 JADX”。建议形成 **`rust_ASC`（快查）→ `JADX`（深反编译）→ `apktool`（资源/重打包）** 的分层；`apkscope` 只在“需要 dump/重签/单 exe”时作为可选替代；`dexsql` 等许可证明确后再评估。
